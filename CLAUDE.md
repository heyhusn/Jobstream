# JobSpy — project memory

Read this first. It exists so future sessions don't need to re-read SETUP.md,
DEPLOY.md, all seven migrations, and the roadmap PDF from scratch. Go to those
source docs only for the details this file intentionally omits.

**Live status:** deployed and end-to-end verified on the real cloud project
(`wtkmrkhaokrcxvkrfyop`, org `jusddluiausmulvfemmh`). The local Supabase CLI
is logged in and linked to it — `npx supabase db push` / `functions deploy`
act on production directly, with no staging environment in between. Treat
any DB/function deploy command as a real production action requiring the
user's go-ahead, not a routine one.

## What this actually is

A job-search web app: auth → resume upload → AI-parsed profile → scored job
matches → Kanban application tracker → AI cover letters. Package name is
`jobspy-app`; there is **no scraper in this repo** despite the name — job data
is static seed rows (`supabase/seed/seed.sql`), not live ingestion.

This repo is **Platform A** of a two-platform master spec
(`implementation_plan.md`). Platform B (a Pakistan→Germany study-abroad
marketplace) is documented there but has zero code in this repo — ignore it
unless the user explicitly pivots to it.

A separate roadmap PDF (`JobSpy_Platform_Research_and_Feature_Roadmap`,
shared in chat, not stored in-repo) proposed a much larger target: FastAPI +
Celery + pgvector + ATS ingestion + agent layer, 25 major + 40 minor
features. **What's built diverges from that plan on purpose** — see below.

## Actual stack (not the roadmap's target stack)

- Frontend: React 19 + TypeScript + Vite 8, Tailwind CSS 4, React Router 7,
  TanStack Query + Virtual, Zustand, `@dnd-kit` (Kanban DnD), `pdfjs-dist`
  (client-side PDF text extraction, no DOCX).
- Backend: **Supabase only** — Postgres, Auth, Storage, Realtime, Edge
  Functions (Deno). No FastAPI, no Celery/Redis, no separate vector DB.
- AI: DeepSeek (`deepseek-chat`) for parsing and cover letters. Matching uses
  Supabase's on-device `gte-small` embedding model (384-dim), not
  OpenAI/pgvector ANN search.
- No Stripe. No LangGraph/agent framework. No Sentry/observability stack.

**Why Supabase-only**: deliberate, documented in SETUP.md as
forward-compatible, not a shortcut needing unwinding. A `tasks` table +
Realtime stands in for Celery/Redis: every AI feature inserts a `tasks` row,
a Postgres trigger (`handle_new_task`) POSTs to an Edge Function via
`pg_net`, the function does the work and updates the row, the client watches
it via Realtime (`src/hooks/useAsyncTask.ts`). Swapping in a real worker
later requires zero frontend changes.

## Feature status vs. the roadmap's 25 major features

Only meaningful for judging what's real. IDs (M01 etc.) match the roadmap PDF.

**Built and working:**
- Auth & Identity (M18) — Supabase Auth, email/password + Google OAuth, route guards.
- LLM Resume Parser (M04) — DeepSeek call on extracted text, confidence + mandatory confirm screen. PDF/txt only, no DOCX.
- Explainable Matching (M05, partial) — score + breakdown + explanation shown in UI, but scoring is cosine similarity (gte-small) + heuristic bonuses, not the full composite the roadmap specced.
- AI Cover Letter Generator (M11) — the most complete AI feature. DeepSeek, credit-gated, tone/notes input, editable, regenerate, placeholder detection, idempotent Edge Function, refund-on-failure. See SETUP.md "Cover letters" section for the full design (worth reading before touching this code).
- Application Tracker / Kanban (M14) — drag-and-drop, stages, notes, next-action dates, resume-version-sent snapshot (minor m23).
- AI Interview Prep Agent (M13) — the first genuinely multi-turn, stateful feature in the app (the roadmap's own "genuine agent" category, distinct from every single-call feature above). `supabase/functions/interview-prep` (+ `prompt.ts`) handles two actions on the `interview_turn` task type (reserved since 0001, finally used): `start` (charges 1 credit, covers the whole session, generates an opening question grounded in the job + resume) and `answer` (evaluates the given answer with feedback + a 1-5 score, then either asks an adaptive follow-up grounded in what was just said, or — once a **hard-capped** `max_turns` of 5 is hit — writes a session summary and marks it `completed`). State lives in a new `interview_sessions` table (schema, RLS: client can only `select` its own rows; every write goes through the service role, same posture as `cover_letters`/`tasks`), not in a LangGraph/agent framework — M17 (Agent Orchestration Layer) is still not built, and a 5-state machine (ask → wait → evaluate → ask-again-or-summarise → done) checked in code is the honest scope for this app's size rather than a framework looking for a reason to exist. The turn cap is enforced by the Edge Function counting `turn_count`, never by asking the model when to stop — the guardrail the roadmap calls non-negotiable for anything agentic. UI: `InterviewPrepPanel.tsx` (mode picker + start button) in `ApplicationDrawer.tsx`, handing off to a dedicated page at `/interview/:sessionId` (`InterviewPrepPage.tsx`) — a 5-turn transcript doesn't fit in the 560px drawer next to two other panels. Deployed and verified with a full real 5-turn technical interview run end-to-end against production: genuinely adaptive follow-ups (each one built on the specific gap named in the prior feedback), a specific and grounded final summary, hard cap correctly enforced at exactly 5 turns, exactly one credit charged for the whole session.
- ATS Resume Optimiser (M10) — `supabase/functions/optimize-resume` (+ `prompt.ts`), a third instance of the `generate-cover-letter` reference pattern, wired into `ApplicationDrawer.tsx` via `ResumeOptimizerPanel.tsx` right above the cover-letter panel. Per-job (not aggregate like the skill gap analyser): compares the resume's `extracted_text` against one specific posting and returns matched requirements (with quoted evidence), gaps (with a suggestion — never inventing what to add), and hard "knockout" requirements (clearance, licence, mandatory years). **Deliberately emits no numeric score anywhere** — see the callout at the top of `prompt.ts` and CLAUDE.md's own note on why a fake "ATS score out of 100" is exactly the thing this project avoids. New task type `resume_optimize` (not pre-reserved like `skill_gap` was — added to `TaskType` and to the dispatch switch together in `0009_resume_optimizer_dispatch.sql`). No dedicated table; result lives on the task row, matched back to its job via `input.job_id`. Deployed and verified live: real, specific output grounded in the actual resume and an actual ingested Greenhouse posting, one credit charged, no double-charge.
- Natural Language Job Search (M06) — `supabase/functions/parse-search-query`, deliberately architected differently from the credit-charging AI features: no `tasks` row, no service-role client, no `TASK_DISPATCH_SECRET` — the client calls it directly via `supabase.functions.invoke`, relying on the platform's default JWT verification rather than the shared-secret pattern, because this function reads and writes nothing (pure text-in, JSON-filter-out) so there's no state to protect. Converts a sentence into a typed filter (`remote_type`, `min_salary`, `keywords`, `max_ghost_risk`) applied client-side against the matches already loaded on `MatchesPage` — not a fresh query, not semantic search. Honest about scope: fields the schema doesn't support (visa sponsorship, company size, etc.) come back in an `unsupported` string instead of being silently dropped, and a low-confidence parse (`confidence < 0.35`) falls back to a plain substring match on the raw query rather than trusting a bad structured guess. Free tier, no credit charge, per the roadmap's own pricing table. Deployed and verified live, including the roadmap PDF's own example query ("remote ML roles paying over $120k that sponsor visas") — correctly filtered what it could and flagged visa sponsorship as unsupported.
- Skill Gap Analyser (M12) — `supabase/functions/analyze-skill-gap` (+ `prompt.ts`), built as a second instance of the `generate-cover-letter` reference pattern (shared-secret auth, conditional task-claim, charge-before-generate with refund-on-failure, retry-once-on-garbled-JSON). Grounds the analysis in the user's own highest-scored active matches (falls back to the most recent active postings if matches haven't been computed yet), diffs required skills against the profile via DeepSeek, returns ranked gaps + strengths + a short narrative. No dedicated table — like `parse_resume`, the result lives on the `tasks` row itself; `useSkillGap.ts` reads the latest completed one. `SkillsPage.tsx` replaced its `<ComingSoon>` stub with a real page. Routing needed a new migration (`0008_skill_gap_dispatch.sql`) — `skill_gap` had been a valid `task_type` since 0001 but `handle_new_task` never had a dispatch case for it.

- Assisted Apply (M15) — scoped to what this app can honestly do: no browser automation, no ATS form-autofill, no headless browser anywhere in this repo. `supabase/functions/assisted-apply` (+ `prompt.ts`) is a fourth instance of the `generate-cover-letter` reference pattern: the user pastes the screening questions a real application form is actually asking (free text, one per line, capped at 12), and it drafts a grounded answer to each from the resume/profile/job. Never fabricates: for anything the resume/profile doesn't literally establish (salary expectations, visa/work-authorisation status, availability, relocation) it returns `insufficient_info: true` with a one-line note on what's missing instead of a plausible-sounding guess — same rule as the resume optimiser's refusal to invent an ATS score. UI: `AssistedApplyPanel.tsx` in `ApplicationDrawer.tsx` (between the resume optimiser and interview prep panels), with a per-answer copy-to-clipboard button since the point is pasting these into an external form. Deployed and verified live with a genuinely adversarial real test — the job used (a "Director, SMB Sales" posting) didn't match the test resume (AI/ML engineering) at all, and the model correctly returned `insufficient_info` for every one of the three questions (motivation, salary, relevant experience) rather than inventing a plausible-sounding fit. One credit charged, no double-charge.
- Smart Job Alerts (M16) — scoped to what this app can honestly do: no scheduler (no pg_cron/Celery Beat) and no email/push infrastructure exist anywhere in this codebase (M22 is still not started), so this is deliberately pull-based, not push. Migration `0014_job_alerts.sql` adds a plain user-owned `job_alerts` table (name + `filter` jsonb + `last_checked_at`), RLS'd for full owner CRUD — the posture of `applications`, not the locked-down service-role posture of `tasks`/`cover_letters`, since nothing here is AI-generated or credit-charged. `useJobAlerts.ts` reimplements the same filter shape/logic as `parse-search-query`'s `SearchFilter`/`matchesFilter` (remote type, min salary, keywords, max ghost risk) but with zero import coupling — every match is computed live, client-side, against a capped recent slice of active jobs, whenever `AlertsPage.tsx` (`/alerts`) is open or "Check now" is pressed. - Unified Job Ingestion Service (M01) — real, not a stub: `supabase/functions/ingest-jobs` pulls live postings from Greenhouse's public keyless JSON board API (no scraping, no auth, the roadmap's own recommended posture) for 4 real companies (Vercel, Figma, Asana, Brex — see `DEFAULT_BOARDS` in the function to add more). Normalizes into the existing `jobs`/`companies` schema, dedupes on a `greenhouse:{token}:{id}` fingerprint, detects relistings (gap >3 days between sightings bumps `repost_count`, feeding straight into the ghost detector), closes out postings that vanish from a board, and isolates per-board failures. Manual invocation only (no scheduler — same limitation as ghost-signal recompute); each run caps at 10 most-recently-updated jobs per board to stay fast and keep `generate-matches`'s per-user embedding loop bounded. One real side effect from first use: ingesting real Vercel data closed out the old hand-seeded fake Vercel demo job, since it doesn't exist on Vercel's actual board and both share the same company row (keyed on domain) — expected, not a bug, but worth knowing if a seeded demo job unexpectedly goes inactive after running this.
- Ghost Job Detector (M07) — deterministic SQL scoring function (`public.compute_ghost_signal`, migration `0007_ghost_job_detector.sql`), auto-recomputed via trigger on job insert/update, backfilled for existing rows. Scores on days-open, repost count, salary disclosure, first-party-ATS-vs-aggregator source; company fill-rate term is wired but dormant until something populates `companies.enrichment->>'fill_rate'`. No scheduler exists yet (no pg_cron/Celery Beat), so a job's `days_open` only re-ages on the next write to that row — call `select public.recompute_all_ghost_signals();` periodically until that's wired up.
- Hybrid Semantic Search (M03) — the roadmap's last real gap, now closed: migration `0023_hybrid_search.sql` adds a generated `search_vector` tsvector column on `jobs` (title weighted above description, GIN-indexed) and an HNSW index on the existing `jobs.embedding` column (cosine ops, matching how `generate-matches` already compares these vectors) — the first ANN index this app actually queries. `public.search_jobs_hybrid(query_text, query_embedding, match_count)` fuses the two independently-ranked top-50 lists via Reciprocal Rank Fusion (`1/(60+rank)` per list, the standard Cormack/Clarke/Buettcher constant) rather than averaging a tsrank score against a cosine distance — those live on unrelated scales, and RRF only needs rank order, not the raw numbers. `supabase/functions/hybrid-search` computes the query embedding with the same on-device `Supabase.ai.Session('gte-small')` call `generate-matches` uses (so the query vector lives in the same space as what it's compared to), calls the RPC with a caller-scoped client, and returns full job/company/ghost-risk details in RRF order with an honest `matched_via: "keyword" | "semantic" | "both"` label per result. Architecturally distinct from M06 (`parse-search-query`) on purpose: M06 filters the matches a signed-in user already has computed against their own profile; this searches the *entire* active job board regardless of whether a match exists yet — free-tier, no `tasks` row, no credit charge, same reasoning as M06 (the embedding call is a cheap on-device model, not a billed LLM). New page `SearchPage.tsx` at `/search` (nav added between Matches and Tracker), reusing `useSaveToTracker`/`useTrackedJobIds` so a result can go straight to the tracker without a precomputed match score. `public.job_embeddings` (vector(768)+HNSW from migration 0001) stays orphaned on purpose — wrong dimension for the gte-small embeddings this app actually produces (384); hybrid search was built on the real `jobs.embedding` column from `0004_real_matching.sql` instead of trying to resurrect it. Deployed and verified live against production: "machine learning engineer" correctly top-ranked Ramp's actual ML Engineer posting via `both` signals, "on-call SRE with Kubernetes experience" (no literal match in the seed data) still surfaced conceptually adjacent backend/platform roles via `semantic` alone, and an unauthenticated request was correctly rejected with 401 by the platform's own JWT gate before the function's code ever ran.

- Admin Console (M24) — real cross-user data, unlike M21's per-user views: `private.admin_users` (an allow-list in the `private` schema, never exposed via PostgREST, same posture as `private.app_config`) gates `public.is_admin()`, which every one of three `security definer` admin functions checks as its literal first statement, raising an exception for anyone else — that check is the real security boundary, not the `/admin` nav link or page (both are UX convenience; `AdminPage.tsx` shows "Not authorised" client-side, but a non-admin calling the RPCs directly gets a hard Postgres exception either way, verified live). `admin_overview()` (users, active jobs, applications, unread notifications, today's total spend/credits across everyone), `admin_task_health()` (task volume by type/status over a recent window, to catch a feature silently failing 100% of the time), `admin_source_health()` — honestly labeled as a proxy: this app has no real ingestion-run log, so "last ingested" is really "the most recent `last_seen_at` among that company's jobs," stated in both the migration and the page. Verified live: the granted admin account gets real data back from all three; a second real account gets `false` from `is_admin()` and a hard exception from `admin_overview()`. `AdminPage.tsx` also has a real Actions panel (run ingestion, recompute ghost signals, send the notification digest) backed by `supabase/functions/admin-action` — the console was read-only monitoring until this, since the two Edge Functions it triggers need `TASK_DISPATCH_SECRET`, a secret that must never reach the browser. `admin-action` holds that secret server-side and re-derives the caller's identity from their own verified JWT (same pattern as `delete-my-account`), checks `is_admin()` against it, and only then forwards to `ingest-jobs`/`send-notification` or calls `recompute_all_ghost_signals` directly via a service-role client. Verified live that both the platform's own JWT gateway and the function reject an unauthenticated/invalid-token request (401 before the function's own code even runs); the admin-authorized path was verified by construction (identical pattern to `delete-my-account`) plus the already-proven `is_admin()`/`recompute_all_ghost_signals` behavior, not by a full live invocation as the real admin (no password on hand to sign in as them from a script).

**m12/m13/m14 (job signal extraction) design note:** all three are deterministic regex/keyword classification over `jobs.title`/`description` — same posture as 0007's ghost detector and m15's remote_type normaliser, not an LLM call (nothing to prompt-inject, nothing to hallucinate, free to run). One shared function, `public.extract_job_signals()` (migration `0025_job_signal_extraction.sql`), computes all three together via an insert/update trigger on `title`/`description`, backfilled for every existing row on deploy. `visa_sponsorship` is two states only (`offered`/`not_offered`) — a posting that says nothing about it gets `null`, not a guessed default, matching this app's house style of never presenting a guess as a fact. `seniority` is inferred from the title (most-specific patterns checked first — e.g. "Senior Engineering **Manager**" lands on `manager`, not `senior`) and defaults to `mid` rather than `null` when nothing matches, since every posting has *some* level even if the title doesn't say so explicitly; because a title-based guess is occasionally wrong (a "Senior" at one company is a "Staff" at another), `seniority_overrides` (same migration) is a plain per-user override table — the classifier's output is shared across everyone, but disagreeing with it can't mean editing what every other user sees, so overriding it is scoped to the user who clicked it. `tech_stack` matches against a fixed ~38-term dictionary with word-boundary regex, deliberately excluding ambiguous bare English words as language names (Go, R, C) to avoid false positives like "go above and beyond" tagging a posting as Go — verified live against real ingested data: real, sensible tags on real postings (e.g. a "Software Engineering Intern" role correctly tagged `TypeScript, JavaScript, Rust`; "Member of the Technical Staff, Financial Data Platform" correctly tagged `Kafka, AWS, GCP, Azure, Snowflake`), and every currently-active posting's `visa_sponsorship` correctly came back `null` since none of them actually mention it — not a bug, an honest result.
